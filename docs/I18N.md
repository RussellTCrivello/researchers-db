# Languages — how the locale system works and how to extend it

SIRAJ is bilingual out of the box (Arabic RTL + English LTR) and language-agnostic by construction:
**no user-visible interface string lives in the code**.

## The three layers

| Layer | Where it lives | What it holds |
|---|---|---|
| Language registry | `app/static/js/locales/index.json` | which languages exist, their direction and display name, which is the default |
| UI bundles | `app/static/js/locales/<code>.json` | flat `key → string` maps (currently 361 keys; EN and AR are exact mirrors) |
| Content | the database | every entity has `*_ar` / `*_en` columns, and `locale` + `vocabulary_label` rows carry reference data in both languages |

```json
// locales/index.json
[
  { "code": "ar", "name": "العربية", "en_name": "Arabic", "dir": "rtl", "default": true },
  { "code": "en", "name": "English", "en_name": "English", "dir": "ltr" }
]
```

`core.js` loads this manifest at boot and uses it for three things: which bundle to fetch, the
`dir`/`lang` attributes on `<html>`, and the order the language toggle cycles through. Nothing else in
the code knows the word "Arabic".

## Adding a language (example: French)

1. Copy `app/static/js/locales/en.json` to `fr.json` and translate the values (keys never change;
   `{n}`, `{u}`-style placeholders must be preserved).
2. Add one line to `locales/index.json`:
   `{ "code": "fr", "name": "Français", "en_name": "French", "dir": "ltr" }`
3. Restart — the toggle now cycles AR → EN → FR. Untranslated keys fall back to English, then to the
   built-in safety net, then to the key itself, so a half-finished bundle is usable and never shows
   an empty label.
4. `python -m pytest -q -k locale` verifies parity; keep `fr.json` in step (the parity test compares
   key sets across every bundle).

Nothing else is required: layout is direction-agnostic (logical CSS properties, `dir`-driven), dates
use the browser locale of the active language, and numbers/codes stay Latin in every language so that
counts and identifiers match exported files.

## Content languages

Record *content* is stored bilingually per field, which is what a bilingual research registry needs
(maintaining the same person's name in AR and EN, not switching one off). Supporting three or more
content languages means moving to the translation table described in `docs/DESIGN_REVIEW.md` §6
(`person_translation(field, locale, value)`); the interface layer above does not change.

## Guards that keep it honest

* `test_locales_have_identical_key_sets` — every bundle has exactly the same keys, all non-empty.
* `test_locale_manifest_declares_every_language` — each declared code has a bundle, and directions are
  `rtl`/`ltr`.
* `test_every_translation_key_used_in_js_exists` — every `t("…")` / `data-i18n` key used in the code
  (and the HTML shell) exists in the bundles; catches typos at test time, not in production.
* `test_no_hardcoded_bilingual_strings_in_ui_code` — refuses inline `lang === "ar" ? "عربي" : "…"`
  copy, so a new language can never be half-supported.
